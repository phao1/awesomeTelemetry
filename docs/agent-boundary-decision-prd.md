## 0. 一页结论

- **要回答的问题**：这个子 Agent（这条委派边界）值不值得存在？不值得的话改成什么？改完有没有变好、有没有哪个任务变坏？
- **主用户**：在 Claude Code、Codex、OpenCode 之上搭建多 Agent 工作流或产品的开发者。他们拥有子 Agent 定义和编排代码，能反复运行自己的系统，最怕改一处坏一片。
- **决策单位是「Agent 定义」**，在多次运行之间聚合。单个运行只是一个样本，作为入口和证据。
- **核心产物是每条边界的「协作收支账」和「判定卡」**。成本是协作税（冷启动、重复读取、主 Agent 等待、交接缺口、薄包装），收益是隔离、并行和独立验证。判定共六种：折回、合并、改为工具调用、保留、拆出、证据不足。
- **不开新菜单，全部在任务中心里完成**。任务页加「架构」页签，打开任务就自动算，只读本地记录、不调模型；任务列表加「架构概况」抽屉做跨任务汇总（定义判定、合并候选、调用链覆盖）；任务列表多选分成 A / B 两组进入「对比」。
- **验证的主干是任务级的分组对比**。A / B 两组可以来自手选、版本区间（分界点前后）或任务模式实验的两臂；相同输入的任务配对，回归置顶。顺序固定为：质量 → 原来子 Agent 的工作后来谁在做 → 调用链覆盖 → 过程 → 开销。两组之间改了几处、每组是不是只有一个样本，都要标出来。只有这一档或受控实验能把判定升为「已验证」。
- **AI 复核在 v1**。用用户自己的模型，对选定的边界做规则做不到的语义判断：交接是否丢了含义、多个定义的指令是否冲突、工具描述是否重叠、反方理由是否成立。复核同时生成迁移草稿：skill、工具说明、返回结构、委派模板。模型结论只能引用证据包里的 ID，不能把判定升为「已验证」。
- **第一步是补数据**：先把 Claude Code、Codex、OpenCode 的委派链补完整，再做其他事（§14）。

## 1. 文章给的决策模型

文章的立场：企业 Agent 往往一个主循环加按需加载的 skill 和工具就够了，子 Agent 常因组织结构（康威定律）被拆得过多。拆错的代价有四类：交接丢细节、提示词互相冲突（Frankenprompt）、各自评测看不到整体、嵌套延迟（一个客户折回后运行时间约快 2 倍）。子 Agent 仍然成立的情况有三种：单循环因上下文膨胀出现可测的退化；需要并行、用完即弃的新上下文；单 Agent 选不对工具或指令互相冲突。

落到产品里是六种判定：

| 判定 | 含义 | 何时成立（文章 / kit） | 本产品可观测的信号 |
|---|---|---|---|
| 折回 | 子 Agent 的流程变成主循环的 skill，API 变成工具 | 独立上下文没换来收益；交接丢细节；嵌套延迟 | 冷启动开销高；主 Agent 委派前后重复读同样内容；主 Agent 干等；没有并行 |
| 合并 | 两个子 Agent 合成一个 | 总是一起被调用、链式依赖对方输出、碰同一份数据 | A 之后紧跟 B 的比例；共享资源；B 的输入引用 A 的输出 |
| 改为工具调用 | 保留独立上下文，但由主 Agent 当工具调用，返回固定结构 | 需要隔离大量读取，但自由文本交接不可靠 | 隔离收益高，但返回后主 Agent 仍追问或重读 |
| 保留 | 维持独立 Agent，必要时配完整交接 | 并行调研；独立验证；读得远多于返回；直接与用户多轮对话或由外部团队拥有 | 实际并行重叠；返回量远小于消耗量且主 Agent 不再重读；审查结论被采纳 |
| 拆出 | 反向：把主循环里的一段工作交给子 Agent | 单循环上下文膨胀导致可测退化；独立子任务被顺序执行 | 上下文逼近上限并触发压缩；压缩后重读或违背约束；一段大量读取只产出少量结论 |
| 证据不足 | 先补采集或补验收 | — | 缺委派关系、返回内容、用量或时间 |

方法照搬文章：先测再改；一次只改一处；逐任务看通过/失败翻转，不只看总分；每个任务多跑几次；模型升级后重新审视。

## 2. 对 v1 清单的判断

**保留**：证据优先；覆盖率与结论分开；规则事实与模型解释分开；回归优先于平均；官方案例用作演示；不自动改用户代码；采集默认关闭；P4/P5 里关于密钥、发送预览、引用校验、费用单列、可取消的护栏。这些 v2 全部继承。

**问题**：

1. **以「问题列表」为中心，而不是以「决策」为中心。** R1–R8 是症状，构建者想知道的是「planner 这个子 Agent 留不留」。症状应汇总成每条边界的一张结论卡。
2. **单任务得不出合并或折回的结论。** kit 的 `coupling_map.py` 和文章说的「经常一起被调用」，都基于多条 trace 的分布。
3. **没有区分用户能动的杠杆。** 改定义文件、改编排代码、改指令是三种不同的改法，建议要落到其中之一才能执行。
4. **价值没有量化。** 没回答「先改哪个、值不值得改」。
5. **验证全靠手动重跑再关联。** 构建者本来就会反复运行自己的系统，系统应自动识别版本、按输入配对，而不是让人逐个关联。
6. **AI 复核的对象和产出不对。** P5 让模型复核「问题」；构建者真正需要模型做的是规则做不到的语义判断，以及把结论变成可用的迁移草稿。
7. **产品设计和给编码 Agent 的护栏写在一起。** 读完看不出用户看到什么、拿走什么。
8. **只讲合并和保留，缺「什么时候该拆出子 Agent」。** 这恰好是「哪种情况适合用主子 Agent」的另一半。

## 5. 价值

对构建者：

- **用真实运行代替猜测**：kit 的审计靠读代码加导出 trace，这里直接用已有的运行记录，每个数字都能点回原始事件。
- **每次改动有回归护栏**：在任务中心里直接把改造前后的任务分成 A / B 两组，按相同输入配对、逐任务翻转置顶，并说明原来子 Agent 的工作后来由谁在做。总分上涨但某个任务退步时，结论是「不支持直接采纳」。
- **迁移材料直接可用**：AI 复核产出 skill 草稿、工具说明、返回结构和委派模板，由构建者自己审阅后落地。
- **持续而不是一次性**：定义变了、模型换了，体检自动更新。

与已有方案的区别：

| | single-agent-loop-kit | 通用 trace 平台（Langfuse 等） | 本产品 |
|---|---|---|---|
| 证据 | 读编排代码，再导出 trace | 能看 trace，没有架构判断 | 直接用 Claude Code / Codex / OpenCode 的真实运行 |
| 判断粒度 | 每个子 Agent 一个判定 | 无 | 每个定义一张收支账，可点回原始事件 |
| 验证 | 自己写评测、跑 `compare.py` | 无 | 自动识别版本、按输入配对，也能接受控实验 |
| 持续性 | 一次性迁移流程 | 持续，但不针对边界 | 定义或模型变化后自动复查 |
| 关系 | — | — | 与 kit 互补，v2 支持双向导出 / 导入 |

## 6. 核心概念

- **Agent 定义**：一类子 Agent。身份 = 工具 + 类型名（Claude Code 的 `subagent_type`、Codex 的角色、OpenCode 的 agent 名）+ 定义指纹。定义指纹取自关联仓库里的定义正文；没有文件（如 Agent SDK 的程序化定义、内置 Explore）时，取自运行中观察到的系统提示，再拿不到就只用类型名。判定挂在定义上。
- **版本**：一组定义在某个时刻的状态，由各定义指纹组成；关联仓库时附提交号。用分界点划分区间，区间是对比分组的一种来源。
- **对比组**：A / B 两组任务。来源可以是手选、分界点前后的版本区间，或任务模式实验的两臂。
- **职责去向**：A 组里某个子 Agent 的典型动作，在 B 组里由谁执行（主 Agent、其他子 Agent、工具或 skill、无人）。
- **调用链覆盖**：范围内能确认父子关系的委派占比。覆盖不足时判定降级、对比标为不可比。
- **运行**：构建者系统的一次顶层执行（一个任务）。
- **输入指纹**：运行首条用户输入的规范化哈希，或用户提供的 case ID，用来跨版本配对。
- **委派**：一次主 → 子调用，包括委派输入、子 Agent 过程、返回内容、用量和时间，是证据的最小单位。
- **边界**：某个父到某个定义的全部委派。判断合并时，也可以是两个定义之间的边。
- **协作收支账**：一条边界上的成本和收益信号，每个数字都能展开到具体委派。
- **判定**：六种之一，附置信度、反证和改法。
- **决策记录**：构建者对某条边界做的决定（采纳、回退、继续调整、保留），以及所依据的报告版本；不覆盖测量结果。

## 7. 协作收支账：信号

成本侧（协作税）：

| 编号 | 信号 | 怎么算 | 指向 |
|---|---|---|---|
| C1 | 冷启动 | 每次委派时子 Agent 首个请求的输入 token（系统提示、工具目录、委派输入）和缓存命中率 | 折回 |
| C2 | 前置重复 | 子 Agent 读取或搜索的资源中，主 Agent 委派前已读过的比例（按规范化路径、范围和内容指纹） | 折回，或补全交接 |
| C3 | 后置重读 | 子 Agent 返回后，主 Agent 又去读子 Agent 读过的资源的比例 | 交接不足 → 改为工具或折回 |
| C4 | 主 Agent 等待 | 子 Agent 运行期间主 Agent 没有活动的墙钟时间 | 折回（在没有并行时） |
| C5 | 往返 / 返工 | 短时间内对同一定义、同一目标再次委派；主 Agent 纠正或追问 | 合并或折回 |
| C6 | 交接缺口 | 委派输入缺少主 Agent 已掌握的关键引用；返回缺少后续用到的内容（沿用现有检查） | 改为工具（结构化返回） |
| C7 | 薄包装 | 子 Agent 只做一两次工具调用就返回 | 折回为直接工具 |

收益侧：

| 编号 | 信号 | 怎么算 | 指向 |
|---|---|---|---|
| B1 | 上下文隔离 | 子 Agent 消耗的内容量 ÷ 返回量，并且主 Agent 之后没有再读（与 C3 一起看） | 保留或改为工具 |
| B2 | 实际并行 | 兄弟子 Agent 活动区间的重叠；节省 = 各自时长之和 − 区间并集 | 保留 |
| B3 | 独立验证 | 审查或验证类子 Agent 的结论被主 Agent 采纳，随后出现对应修改 | 保留 |
| B4 | 工具 / 指令隔离 | 子 Agent 用了主 Agent 没有的工具集；主工具目录超过 30–50 个 | 保留，或先修工具 |
| B5 | 对话 / 所有权 | 子 Agent 直接与用户多轮对话，或由外部团队拥有（来自定义或构建者声明，无法观测） | 保留 |

质量侧：

- **主来源是验收结果**：导入构建者自己的验收输出（沿用 benchmark 的 verdict 格式，逐 case），或在界面上逐个标记通过/失败。
- **代理信号只展示，不参与判定**：用户纠正、会话内测试结果、同一文件反复修改。

## 8. 判定规则 v1

规则是本产品的启发式：版本化、阈值可调，报告记录所用版本，不冒称是文章给出的公式。

| 判定 | 候选条件（全部满足） | 主要反证 |
|---|---|---|
| 折回 | C1、C2、C4 至少一项显著；B1 低或 C3 高；B2 ≈ 0；没有 B3、B5 | 有被采纳的独立验证；读量远大于返回且主 Agent 不重读 |
| 合并（X、Y） | Y 紧跟 X 出现的比例高；共享资源；Y 的输入引用 X 的输出 | 两者工具集差异大；各自被单独调用也很常见 |
| 改为工具调用 | B1 高，但 C3 或 C6 高 | 返回已有稳定结构 |
| 保留 | B1 高且 C3 低；或 B2 显著；或有 B3；或有 B5 | 协作税远高于收益 |
| 拆出 | 单循环上下文持续增长并触发压缩；压缩后出现重读或违背约束；一段大量读取只产出少量结论；独立子任务被顺序执行 | 后续步骤依赖这段工作的中间细节 |
| 证据不足 | 缺委派关系、返回内容、用量或时间之一 | — |

**置信度三档**：

- 观察：委派次数少（例如不到 5 次）或只来自一次运行。
- 一致：多次委派、多次运行，方向一致。AI 复核最多支持到这一档。
- 已验证：有任务级分组对比或受控实验支撑，每个相关输入至少 3 次可比运行，且有验收结果（与现有 agent-folding 契约 AF-003 一致）。

**优先级 = 可争取空间**：所选范围内这条边界可归因的协作税总量（token 和时间）。例如「近 200 次运行中 47 次委派，冷启动加重复读取共 1.2M token，占总量 8%」。这是已发生的事实，不是承诺的节省。

## 9. AI 复核（v1）

**做什么**：构建者在判定卡上主动点「AI 复核」，范围是一条或几条边界。模型只做规则做不到的五件事：

1. **交接语义**：委派输入是否带上了子 Agent 需要的含义（不只是字面引用）；主 Agent 是否真正用了返回结果。
2. **指令冲突**：主循环和各定义的提示词之间是否有互相矛盾的规则（Frankenprompt）。
3. **工具重叠**：工具描述是否相近到容易选错，与 B4 一起看。
4. **反方论证**：针对规则给出的判定，按文章的保留条件找反证；规则判「保留」时，也找折回的理由。
5. **迁移草稿**：按判定生成 skill 草稿、工具说明、返回结构（结论 / 依据 / 已执行动作 / 置信度 / 注意事项，与 kit 一致）和委派模板。

**发送什么（证据包）**：定义正文（关联仓库时）、规则事实与数字、有代表性的委派（同时包含正例和反例）、已知缺口。发送前展示接收方、模型、包含内容和删减情况，并给出 token 估算；可以排除片段。

**返回什么**：结构化结果。每条结论必须引用证据包里的 ID，推测和事实分开写；附建议、复测项和草稿。引用不存在、越界或格式不对的结论直接拒绝。

**连接与护栏**（沿用 v1 清单 P4/P5）：

- 支持 Anthropic Messages 和 Chat Completions 兼容两种协议，可配企业网关或本地模型。
- 密钥默认只存在服务进程内存，不进浏览器存储、日志、报告或导出。
- 只能由显式 POST 触发，页面加载和轮询不会触发；可取消；不自动重试；不在后台批量调用。
- 复核用量单独计费、单独显示，不并入被观测系统的开销。
- 模型没有工具权限，trace 内容按不可信数据处理。

## 10. 用户路径与界面（r3：全部放进任务中心）

### 10.1 现状和原则

本地最新版本（`codex/agent-team-observability` 及其工作区 `codex/page-layout-audit`，2026-10-30 实测）的顶部导航是「任务中心 · 数据接入 · 评测中心 · 任务模式实验 · 设置 · 兼容统计 ▸」。没有叫「对比中心」的页面。现有和对比相关的有三处：

| 现有位置 | 比什么 | 粒度 | 在 r3 里的角色 |
|---|---|---|---|
| 兼容统计 ▸ 对比（`CompareBoard`、`CompareKPI`、`CompareDimensions`） | 两个会话的耗时、Token、运行活动 | 会话级、一对一 | 保持不变。其中「差值不判优劣」「不完整记录不出整体差值」的组件和口径，在任务级对比里复用 |
| 任务模式实验（`TeamExperimentCenter`、同步回放） | 同一任务在单 loop / 主子 Agent / Team 下各跑 N 次 | 计划好的成对实验 | 降为对比页「还没有对照组？」的入口；实验的两臂可以一键作为 A / B 组 |
| 评测中心（benchmark） | 固定用例集的通过情况 | 用例级 | 验收结果的来源之一（verdict 格式导入） |

原则：

1. **不加顶层菜单**。构建者已经在任务中心里看任务，架构判断跟着任务走。
2. **打开即算，算得便宜**。「架构」页签只读本地记录、不调模型、不启动采集；要调模型的 AI 复核永远是手动按钮。
3. **单个任务只给证据，结论挂在定义上**。任务页里出现的「折回 / 合并」都写成「这个定义跨 N 个任务的判定是……」，并链接到架构概况。
4. **对比在任务级、按组**。会话级一对一对比留在兼容统计里。

### 10.2 三个入口

```
任务中心
├─ 任务列表
│   ├─ [架构概况] 抽屉 ……………… 跨任务汇总：定义判定、合并候选、调用链覆盖（S1、S5）
│   └─ 多选 → 设为 A 组 / B 组 → [对比] …… 任务级分组对比（S3）
└─ 任务页
    └─ 页签：轨迹 · 对话 · 原始 · 架构 …… 本任务的边界账（S2、S4）
```

### 10.3 任务页「架构」页签

在现有「轨迹 · 对话 · 原始」后加「架构」。打开任务时后台就开始算，切过来时通常已经算好。

内容从上到下：

1. **本任务的调用链**：主 Agent → 各子 Agent 的委派树，每个节点标关联等级（已确认 / 只有父侧 / 未关联）。有未关联的委派时，顶部说明「本任务有 N 次委派找不到子会话，以下统计不含它们」。
2. **每条边界的账**：一条委派边界一行，列出冷启动、前置重复、父等待、消耗:返回、并行；每个数字能点回轨迹里的具体事件。
3. **定义级判定（只引用，不在这里下结论）**：「code-reviewer 跨 31 个任务的判定：折回候选 · 一致」→ 打开架构概况并定位到该定义。本任务是反证时（例如这次独立审查确实发现了问题）单独标出。
4. **拆出提示（v1.1）**：主循环上下文压缩、长段只读探索等片段。
5. **AI 复核**（手动）：对本任务里的某条边界发起，证据包只含本任务。

现有「分析拆分与合并」（`ArchitectureDiagnosisPanel`）的三类检查并入这里，不再挂在轨迹下方。

### 10.4 任务列表「架构概况」抽屉

从任务列表顶部的「架构概况」按钮打开，范围跟随列表当前的筛选（工具、项目、时间）。这是 S1 的主页面，也是文章里「合并候选」和「调用链覆盖」两条要求唯一能落地的地方：这两件事都必须跨任务才看得出来。

- **顶部：调用链覆盖**。范围内多少任务、多少次委派，其中几成能确认父子关系，按工具分开显示。覆盖不足时整页的判定降级，并说明缺口在哪（例如「Claude Code 子 Agent 文件写的是父会话 ID，已修复前的记录无法关联」）。
- **定义表**：每个定义一行，按可争取空间排序（示意数据）：

| Agent 定义 | 涉及任务 | 委派次数 | 占 token | 协作税主因 | 收益主因 | 判定 |
|---|---:|---:|---:|---|---|---|
| code-reviewer | 31 | 47 | 11% | 前置重复 72% | 独立验证 5 次 | 折回候选 · 一致 |
| researcher | 58 | 132 | 9% | 冷启动 9k/次 | 隔离 14:1 | 保留 · 一致 |
| test-runner | 22 | 38 | 4% | 薄包装（2 步） | — | 折回为工具 · 一致 |
| 主循环 | 64 | — | — | 上下文压缩 9 次 | — | 拆出候选 · 观察 |

- **合并候选**：定义对，例如「planner → implementer：21 次中 90% 紧跟出现，读取重叠 64%」。
- **选中一行展开判定卡**（内容同下），「查看涉及的任务」会把任务列表筛到这些任务，便于接着多选做对比。

**边界判定卡**（示意数据）：

```
code-reviewer · Claude Code · agents/code-reviewer.md（指纹 a1f3… · 提交 4031f90）
判定：折回候选 · 置信度「一致」（31 个任务中 47 次委派）
一句话：它每次都重读主 Agent 刚改过的文件，独立上下文没有换来隔离收益。

成本
  冷启动         14.2k token/次，缓存命中 19%
  前置重复       72% 的文件主 Agent 委派前已读过
  主 Agent 等待  平均 2 分 10 秒/次
收益
  隔离           消耗:返回 = 6:1（偏低）
  并行           无（总是单独运行）
  独立验证       5 次结论被主 Agent 采纳 ⚠

反证：47 次中有 5 次发现了主 Agent 遗漏的问题。若看重独立审查，选方案 B。

方案 A 折回：定义正文转为 skill「code-review」；删去主提示里「改完代码调用 code-reviewer」
方案 B 保留并精简交接：委派时附改动文件清单和 diff；返回固定结构

[AI 复核（约 18k token）]  [生成迁移草稿]  [记录决定…]  [查看涉及的任务]
```

### 10.5 任务级分组对比

**进入方式**（三种，最终都是 A / B 两组任务）：

| 方式 | 操作 | 典型场景 |
|---|---|---|
| 手选 | 任务列表多选 →「设为 A 组」/「设为 B 组」→「对比」 | 改造前后各挑几次运行 |
| 版本区间 | 判定卡或决策记录上的分界点 →「对比分界点前后」 | 记过决策、标过分界点之后 |
| 实验两臂 | 任务模式实验的结果 →「在任务中心对比」 | 计划好的受控实验 |

还没有对照组时，对比页显示「还没有对照组？」：跳到任务模式实验（自动带上 A 组的输入和定义）或逐 Agent 工作台。

**页面顺序固定**，前面的不成立就不看后面的汇总：

```
A：有 code-reviewer（9 个任务）   B：折回为 skill（9 个任务）   按输入配对 3 组，每组 3 次
⚠ 两组之间改了 2 处：code-reviewer 定义、模型 claude-x → claude-y。差异不能只归因于折回。
结论：不支持直接采纳 — 1 个输入回归
```

1. **质量**：逐输入的通过情况，回归置顶，可展开到失败的那次。没有验收结果时显示「质量未验证」，后面各节照常显示但结论不升级。

| 输入 | A | B | 变化 |
|---|---|---|---|
| case-07 修复登录超时 | 通过 3/3 | 通过 2/3 | ⚠ 回归 |
| case-11 重构缓存层 | 通过 2/3 | 通过 3/3 | 改善 |
| case-02 新增导出接口 | 通过 3/3 | 通过 3/3 | 不变 |
| 另 3 个输入只在 A 出现 | — | 未运行 | 无法判断 |

2. **职责去向：原来子 Agent 的工作后来谁在做**。按 A 组里该子 Agent 的典型动作（读哪些文件、跑哪些命令、做哪类检查）去 B 组里找执行者：

| A 组里 code-reviewer 做的事 | B 组里由谁做 | 覆盖 |
|---|---|---|
| 读改动文件 | 主 Agent（本来就读过） | 9/9 |
| 跑 `npm test` | 主 Agent | 7/9 |
| 写审查结论 | 主 Agent 调 skill「code-review」 | 6/9 |
| 找出主 Agent 遗漏的问题 | 无人 | ⚠ 0/9（A 组曾有 2 次） |

「无人」的行和质量回归放在一起看：这通常就是回归的原因。

3. **调用链覆盖**：两组各自能确认父子关系的委派占比。两组覆盖相差大时（例如一组 95%、一组 40%），过程和开销的差异标为「不可比」。
4. **过程**：委派次数、父等待、前置重复、上下文压缩次数、主循环步数。
5. **开销**：耗时、token、缓存命中的中位数差。只在最后显示，均值提升不能抵消回归。

**始终标出的风险**：

- **一次改了几处**：比较两组的定义指纹、模型、主指令文件、工具权限，列出全部不同点。多于 1 处时顶部黄色提示。
- **样本太少**：某个输入每组只有 1 次时，该行标「单样本」，不计入「支持采纳」的门槛。
- **只有一侧**：只在一组出现的输入显示「无法判断」，不算改善。

### 10.6 完整路径

```
① 接入：数据接入里选工具和项目目录 →（可选）设置里关联定义所在的仓库
② 任务中心 → 架构概况：看调用链覆盖、定义判定、合并候选
③ 选定义 → 判定卡 →（可选）AI 复核 → 迁移草稿 →「记录决定」并标分界点
④ 构建者自己改代码，用自己的方式再跑（测试输入集或日常使用）
⑤ 判定卡「对比分界点前后」，或任务列表多选分 A / B → 对比
   没有对照组 → 任务模式实验跑一组
⑥ 回到决策记录：采纳 / 回退 / 继续调整；定义或模型变化后，概况抽屉提示复查
单个任务出问题时：任务页 →「架构」页签 → 链到定义判定 → 回到 ③
```

## 11. 建议落到构建者的杠杆上

| 判定 | 定义层（Claude Code 子 Agent 定义、OpenCode agent 配置、Codex 角色配置） | 编排代码层（Agent SDK、插件、自研编排） | 指令层（主提示、CLAUDE.md / AGENTS.md） |
|---|---|---|---|
| 折回 | 定义正文转为 skill；工具约束改为权限设置或 hook | 子 Agent 调用换成直接工具；硬约束放进工具 | 删去委派指令 |
| 合并 | 两个定义合成一个，合并工具列表 | 合并两个调用点 | 更新路由说明 |
| 改为工具调用 | 定义里加固定返回结构 | 包装为工具，用共享返回 schema | 说明何时调用 |
| 保留并修交接 | 委派输入模板：必带的文件、约束、已知结论 | 交接协议 | — |
| 拆出 | 新增定义，限定返回内容 | 新增子 Agent 调用或并行工具批 | 写明哪类任务交给它 |

产出物统一是**可复制的草稿或差异**，由构建者自己改，不自动改任何文件。

## 12. 验证闭环

| 档位 | 做法 | 能说明什么 |
|---|---|---|
| 任务级分组对比（主干） | A / B 两组来自手选、分界点前后或实验两臂；按输入指纹配对；质量取自导入的验收结果或手工标记，没有就显示「质量未验证」 | 按顺序给出质量、职责去向、调用链覆盖、过程、开销；满足 §8 条件时可升为「已验证」 |
| 观察期对比（v1.1） | 输入不重复（日常使用）时，比较前后窗口的同类委派 | 趋势；任务分布不同，不能当作因果 |
| 受控实验 | 用现有 agent-folding / benchmark CLI，或 v2 起导出给 kit | 固定变量下的逐任务结果 |

统一规则：通过变失败的任务优先显示，均值提升不能抵消；只有一侧有数据的输入显示「无法判断」，不算改善；两组的定义、模型、主指令、工具权限或验收标准有不止一处不同时，全部列出并提示差异不能只归因于一处改动；每组只有 1 次的输入标「单样本」，不计入采纳门槛。

## 14. 数据就绪度（P0 必须先核实）

每次委派都需要：父子关系、定义名、委派输入、返回内容、子 Agent 用量、子 Agent 的工具调用及参数、时间区间。下面是读代码后的初步判断，需要逐项用真实运行核实：

| 工具 | 初步判断 | 已看到的依据 | 需要补的 |
|---|---|---|---|
| Claude Code | 主会话里的委派调用（类型、输入、返回）大概率可得；子 Agent 过程与主会话的关联看起来尚未建立 | 适配器 `isSubagent` 固定为 false；hooks 支持 SubagentStart/Stop；Mission 用启发式抽取 `subagent_type` | 子 Agent 过程文件与主会话关联；Agent SDK 运行的会话落盘位置和程序化定义的指纹来源 |
| Codex | 部分可得 | 有 `thread_spawn`、`parent_thread_id`；gotchas 记录部分版本只有 `thread_source=subagent`，没有父链接 | 缺父链接时的处理（保留未解决，不按时间猜）；角色名的稳定来源 |
| OpenCode | 部分可得 | 有 `parentID`；子 Agent 识别目前靠标题规则 | 改用 `parentID` 和 agent 名作为主依据 |

验收标准：三个工具各有一组真实多 Agent 运行，委派七项字段齐全或明确标出缺失原因；缺失、截断、重复、错配四类负例不会产生虚假事实。

## 15. 范围与分期

**v1** 分三个可以单独演示的里程碑：

- **M-a 账与判定（不需要模型）**
  1. 补齐三个工具的委派记录（§14）。
  2. 标准化委派记录、定义身份、版本归组。
  3. 可选的只读仓库关联，生成 Agent 清单。
  4. 收支账 C1–C4、C6、C7、B1、B2，加上合并所需的共现统计；判定、置信度、排序。
  5. 任务页「架构」页签（打开即算）；任务列表「架构概况」抽屉（调用链覆盖、定义表、合并候选、判定卡）；证据跳转。
- **M-b AI 复核**
  6. 分析模型配置（两种协议）、证据包预览与删减、结构化返回与引用校验、作业状态与取消、用量单列。
  7. 五类复核和迁移草稿。
- **M-c 分组对比与决策**
  8. 任务列表多选分 A / B 组，或由分界点、实验两臂生成分组；输入指纹配对；验收结果导入和手工标记；按「质量 → 职责去向 → 调用链覆盖 → 过程 → 开销」展示；标出改动处数和单样本。
  9. 决策记录，以及定义或模型变化后的复查提示。

**v1.1**：拆出候选；C5、B3；观察期对比；分析包导出；U1 的简化入口。

**v2**：与 kit 双向导出 / 导入；受控实验一键生成；Team 模式专属判定；OTel 和通用 trace 接入。

**不做**：自动修改用户配置或代码、自动重跑业务任务、自动开启采集、通用 Agent 排行榜、把单次观察说成已证明的收益。

## 16. 成功指标

- 从关联仓库到看到第一条带证据的判定，不超过 3 分钟。
- 判定反馈：构建者对判定点「同意 / 不同意（附原因）」的比例；不同意的原因用来调规则。
- AI 复核：引用校验通过率；生成的迁移草稿被采用的比例。
- 回归护栏：采纳前在分组对比里发现回归的次数。
- 数据就绪度：三个工具「证据不足」的占比持续下降。

## 18. 风险

- **小样本**：构建者的测试输入往往不多。逐任务结果必须显示次数，「已验证」门槛不能降。
- **阈值误伤**：独立审查类子 Agent 天然会重复读取，判定必须同时列反证；「观察」档不给强建议。
- **数据不全却给出强结论**：数据就绪度显示在总览顶部，缺字段直接降为「证据不足」。
- **模型复核的幻觉**：靠引用校验和「最多支持到一致」来约束；复核结论与规则事实分开展示。
- **复核费用和密钥**：发送前给出估算；密钥只存在内存；不自动重试。
- **口径不一致**：各工具的 token 和缓存口径不同，不做跨工具比较，只在同一工具内排序。
