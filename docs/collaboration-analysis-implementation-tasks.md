# Agent 协作分析与优化实施任务清单

为 6.1 实现已确认的第一版：从一个已经观测的任务出发，发现协作问题、定位真实证据、给出调整建议；用户自行修改 Agent 并再次运行，再关联新任务验证问题和收益。没有优化后任务，也能完成首次诊断。

编制日期：2026-10-29。代码核对基点：`codex/agent-team-observability`，HEAD `7b0a4d5`，另有大量未提交的诊断、实验及性能修复。下列复用项是现有实现入口，不代表本轮已验收。所有实施任务保持未勾选，完成后附验证依据再勾选。

## 一 交付目标和范围

主流程：**已观测任务 → 协作分析 → 问题与证据 → 调整建议 → 用户修改并重跑 → 关联优化后任务 → 对比并决策**。

第一版必须做到：

- 在现有任务详情里分析当前任务，无需先建立实验项目、上传两份报告或配置模型。
- 免费规则分析先给可核实的事实；用户配置自己的模型 API 后，可主动请求语义复核。
- 每条结论回答“涉及谁、哪里有问题、证据在哪、为何建议这样改、怎样验证”。
- 输出具体边界建议：合并哪些成员、折回主循环、保留独立上下文作为工具、保留独立 Agent，或先修交接和工具约束；允许结论为待核实。
- 关联优化后任务时同时检查过程问题、任务质量和开销；更快但质量退步必须清楚显示。

本版不做：自动修改用户 Agent 代码、自动重新执行业务任务、自动启动抓包、通用 Agent 排行榜、自动采纳改造、要求安装 Claude Code 才能分析。既有命令行实验能力保留，但不扩展成网页任意付费执行器。

监控、本地代理、Frida、CDP 继续默认关闭。读取历史、查看官方案例、规则分析和模型复核均不能隐式启动采集。分析模型产生的消耗单独统计，不混入目标任务。

## 三 实施顺序

| 阶段 | 交付物 | 前置依赖 |
|---|---|---|
| P0 | 工作区基线、范围和契约差异清单 | 无 |
| P1 | 数据、API、覆盖状态和资源预算契约 | P0 |
| P2 | 可追溯的统一证据输入 | P1 |
| P3 | 规则检查、保留理由、调整候选 | P2 |
| P4 | 网页模型配置及两类协议适配 | P1 |
| P5 | 有界、只读、可取消的模型复核 | P3、P4 |
| P6 | 任务内完整分析和证据交互 | 先接 P3，随后接 P5 |
| P7 | 优化后任务关联、对比和用户决策 | P2、P3、P6 |
| P8 | 官方客服示例和端到端验收数据 | 贯穿 P2 至 P7 |
| P9 | 全量检查、性能、构建和浏览器验收 | P0 至 P8 |

优先交付三个可演示的小闭环：① 一个任务无需模型即可发现问题并跳到证据；② 配置模型后可复核具体边界；③ 关联一次优化后的真实任务，看到问题变化和质量回归。随后补齐边界场景，不先搭建通用实验平台。

## 四 详细任务

### P0 核对基线和范围

- [ ] P0.1 记录当前分支、提交、已修改及未跟踪文件；分别标记已有诊断、官方数据、实验和性能修复，明确本次可修改文件。验收：无丢失、覆盖或误纳入的原有改动。
- [ ] P0.2 阅读 `AGENTS.md`、`BOOTSTRAP.md`、相关契约、模块 spec 和 gotchas，确认是 M12 之后的增量。核对实际依赖版本，不用旧文档的版本描述回退依赖。
- [ ] P0.3 建立 `add-task-collaboration-analysis` OpenSpec 变更，补 proposal、spec delta、design 和指向本清单的执行任务；先记录新旧语义差异。重点处理“CLI 才能付费执行”与新增“网页只读模型分析”的边界，旧 GET 继续免费只读。
- [ ] P0.4 对拟复用的诊断、folding、任务路由运行相关测试，记录已有失败与待核实能力；保留本轮开始时的构建和监控配置。验收：后续能区分新回归与已有问题，并在最终交付前修好所需检查。

### P1 先确定数据和接口契约

- [ ] P1.1 定义分析快照：绑定任务、来源、成员范围、源修订、分析时间、策略版本、阈值及采样范围；模型复核另记模型、提示版本、证据摘要指纹和用量。原始任务变化后，旧报告标为历史或过期，不能冒充当前状态。
- [ ] P1.2 扩展证据引用：保留现有原生事件、HTTP 捕获、Codex 逻辑调用定位；导入记录有自己的来源、记录标识和字段路径，不伪装原生事件。定义父子关系、读取资源、调用结果和交接事实的可用性及完整性。
- [ ] P1.3 定义检查结果与覆盖率两个独立维度。检查结果支持“发现问题、范围内未发现、证据不足”；覆盖率包含已检查、总量或未知、省略、截断和原因。有部分发现时仍须展示未覆盖范围。
- [ ] P1.4 定义事实、模型解释、调整候选、反对理由和用户决定的独立结构。建议必须定位到具体成员或边界；加入待核实状态，修复非主成员默认 `as_tool` 的倾向。没有证据不输出确定的合并或保留结论。
- [ ] P1.5 定义基线与候选的关联、逻辑角色映射、质量依据、可比条件和决策记录。支持多成员合为一个、一成员拆为多个；不把来源类型、临时 Agent ID 或显示名称当版本身份。
- [ ] P1.6 在权威契约里登记配置、显式分析作业、状态读取、取消、报告读取、任务关联和决策保存的 API；复用 Host/Origin、防跨来源访问、ApiError 和前台响应保护。新付费动作必须是显式 POST，不能由 GET、页面加载或轮询触发。
- [ ] P1.7 确定报告与关联的本地持久化、原子写入、版本升级、保留上限和删除语义；如新增表，先写 DDL 与索引。列表只读元数据，正文按需读取；不复制完整 trace 到每份报告。原文删除后证据链接显示不可用，不能通过旧报告绕过删除。

阶段验收：新增字段、枚举、错误和容量都有正式契约；源码按契约实现，不在组件里临时拼一个不可追踪的报告。

### P2 整理真实证据

- [ ] P2.1 为采集和导入分别提供能力矩阵，按实际数据决定能检查什么。导入只包含摘要或最终结果时仍可打开任务，但相关检查明确不足。官方历史日志、合成流量、离线 smoke 分别保留来源说明。
- [ ] P2.2 提取并关联实际模型调用、工具提议、执行、结果和所属成员；沿用已验证的任务关联。一个调用在原生日志和抓包中重复出现时去重，无法确认则不合并、不双算。
- [ ] P2.3 实现读取资源标准化：工具别名、项目与工作目录、规范资源标识、参数、读取范围、内容或版本指纹、成功状态、缓存情况。相同文件名但不同目录、内容或范围不得直接判定同一次重复读。
- [ ] P2.4 提取边界两侧证据：实际委派、目标身份、发送内容、接收上下文、返回结果及后续使用。父子关系、工具声明、相邻时间只能提供线索；缺明确关联就保留未解决。接收上下文包括实际可见的继承内容，不能只看委派消息。
- [ ] P2.5 保留单次模型输入的组成和计量口径，区分历史、工具目录、工具输出、系统约束和增量请求。会话累计 Token、WS 整条连接或截断预览不能代替完整模型上下文。
- [ ] P2.6 建立规则和模型共用的有界证据选择器：优先相关边界、发生前后及反例，保留事件顺序；超限显式省略。验证读取前后修订、删除和成员绑定，拒绝混合两个版本的证据。

阶段验收：至少一组真实结构的采集任务和一组导入任务能得到可定位证据；缺失、截断、重复、错配四类负例均不会生成虚假事实。无需启动采集补历史缺口。

### P3 实现规则检查和建议候选

以下 R 编号用于任务追踪，不代表上游 kit 的原生规则编号。阈值是本产品启发式，须可解释、版本化，不能冒称文章给出的通用公式。

| 检查 | 不调用模型可确认什么 | 模型或人工进一步判断什么 |
|---|---|---|
| R1 重复读取和查询 | 同一范围内重复成功读取、参数和结果相同等事实 | 是否有必要，是否因交接不足而重建上下文 |
| R2 交接信息缺口 | 显式要求、发送和接收记录中的引用差异 | 转述是否保留含义，缺失是否影响后续决定 |
| R3 紧耦合与反复往返 | 实际顺序、交接次数、显式数据依赖 | 是否共享中间状态、能否合并、独立价值是否仍存在 |
| R4 薄包装和职责重叠 | 重复短调用路径、可见工具及角色定义 | 是否只是转发，折为工具或 skill 是否保留约束 |
| R5 上下文增长和重复携带 | 同口径输入变化、完整内容重复、目录规模 | 哪些上下文无关，拆分、按需加载或保留更合理 |
| R6 工具和指令冲突 | 同名异 Schema、明确调用契约错误 | 相近工具选择歧义、指令冲突与错误原因 |
| R7 保留独立边界的理由 | 显式所有权、独立验收、并行任务和输入范围 | 独立审查、一次性上下文、外部多轮对话是否需要保留 |
| R8 协作浪费扩展检查 | 有明确事件的重复失败、取消后继续执行、排队和等待 | 输出是否无用、资源争抢是否由架构引起 |

- [ ] P3.1 实现 R1，展示重复次数、涉及成员、资源和每次调用证据。排除或降级内容更新、不同范围、失败后重试、独立复核和必要刷新；重复读不直接推出交接失效或合并建议。
- [ ] P3.2 扩展 R2，保留现有完整接收输入和精确关联门槛；把“未出现原样引用”与“语义信息丢失”分开。为同义转述、共享继承上下文和被截断接收记录添加反例。
- [ ] P3.3 实现 R3，分别记录相邻调用频次、实际往返和已确认依赖。无依赖证据时只给审查线索，不输出必然耦合；不把并行时长求和冒充主流程等待。
- [ ] P3.4 实现 R4 候选筛选，将实际行为与可获得的提示词、工具及返回约束一起列出。短路径或同名角色本身不足以判定多余；缺角色定义仍能分析行为，但降低结论范围。
- [ ] P3.5 复用并完善 R5，区分正常携带历史、缓存命中、单请求重复副本和持续输入增长。报告测量依据；可建议按需加载，也可提出独立调查拆分候选，不能以 Token 多直接证明质量下降。
- [ ] P3.6 复用并完善 R6，区分提议与真实执行、参数契约错与权限或网络失败；指令含义冲突交给语义复核。修复目录和约束应作为可选改法，不把所有错误归因于多 Agent。
- [ ] P3.7 实现 R7 保留理由及反对合并的证据检查，覆盖独立验证、并行探索、可丢弃大上下文、外部所有权和直接多轮业务会话。缺证据时显示待核实，不按角色名称自动保留。
- [ ] P3.8 实现 R8 中有明确事件依据的基础检查，标为产品扩展；没有取消、等待或输出消费证据时跳过对应结论。不能因主回复未引用某段文本就判为子 Agent 白干。
- [ ] P3.9 将所有结果汇成边界建议：支持证据、反例、适用条件、可选改法、风险和复测项。多条规则指向同一事件时去重；不提供 Agent 数量评分或强制二选一的“拆／合”判决。

阶段验收：每类规则都有正例、合理行为反例和证据不足例；一个完全无 API Key 的用户能得到有用的事实报告。

### P4 接入用户自己的分析模型

- [ ] P4.1 增加模型配置界面：连接名称、协议、API 地址、模型名和密钥；支持 Anthropic Messages 与 Chat Completions 兼容协议。明确这是“分析模型”，不改变被观测 Agent 的模型或连接配置。
- [ ] P4.2 第一版密钥默认只保存在服务端进程内存；服务重启后提示重新输入。已有环境变量可作为只读已配置来源。非秘密配置可持久化；密钥不得进入浏览器持久化、响应、日志、导出和报告。若要持久保存密钥，另行实现真实密钥管理，不以同目录保存加密钥匙冒充保护。
- [ ] P4.3 建立专用只读分析客户端，按协议归一化文本、停止原因和用量，复用有界读取与取消。用原生 fetch 等现有能力实现，不添加运行时依赖、不把实验执行器直接暴露给网页。
- [ ] P4.4 校验自定义地址、协议和重定向，避免向另一主机转发密钥或请求回环到本服务；允许用户明确配置合法企业网关或本地模型，不能粗暴禁用所有私网地址。新增连接不得自动探测其他供应商。
- [ ] P4.5 实现用户主动“测试连接”的最小请求，并提示可能产生少量模型费用。覆盖认证失败、模型不存在、限流、超时、协议不兼容和成功；不发送真实任务正文，不触发工具，不自动重试或换供应商。
- [ ] P4.6 用本地协议服务验证两类适配器、错误和超限，不调用真实付费模型。可用模型由用户配置，不能把官方历史实验中的模型名设为默认可用模型。

阶段验收：无 Key 仍可规则分析；配置后状态清楚且不泄密；分析连接与既有 CLI 业务实验权限完全分开。

### P5 实现模型语义复核

- [ ] P5.1 增加“AI 深度分析”显式动作，允许复核当前报告中的选定边界或有界任务范围。调用前展示接收方、将发送的证据范围、删减情况、模型和输出上限；未配置时引导配置，原规则结果保留。
- [ ] P5.2 构造最小证据包：任务目标、相关角色定义、规则事实、边界前后记录、已知缺口和反例。不要只复核规则已命中的边界；对未命中的边界也安排有界语义检查，并明确覆盖数量，避免漏掉纯语义交接和指令冲突。
- [ ] P5.3 发送前去除凭据等不必要秘密，允许预览和排除片段；不改写原始抓包数据。记录删减影响，不把删减后的缺词判成原始交接丢失。分析材料作为不可信数据输入，模型无工具或命令执行权限。
- [ ] P5.4 设计并校验结构化返回：检查类型、事实引用、推测、反证、建议、适用条件和复测项。模型只能引用本次证据包中的 ID；拒绝不存在的证据、越界成员、畸形或截断结果。模型补充不能覆盖已核实事实，也不能自造“证据充分”。
- [ ] P5.5 实现有界作业状态、进度、取消、超时、错误和显式重试；防连点重复计费，保存请求身份和所用配置版本。默认一次有界审阅，不启动多个分析 Agent；超出范围时让用户缩小范围，不能后台无限分片调用。
- [ ] P5.6 在契约中固定单次输入、输出、超时、并发和报告大小上限。服务重启或取消后不自动续费执行；取消只代表停止本地等待或请求，已产生的上游消耗可能仍存在。返回未知费用时如实显示，不写成零。
- [ ] P5.7 保存可复查的模型报告和独立用量记录，区分规则事实、AI 解释和用户判断。源数据变化时保留历史报告并标过期；重新分析由用户触发。分析请求不能污染目标任务的证据和费用。

阶段验收：用本地模拟协议响应验证有用结论、错误结论和恶意 trace 文本；无证据的确定性结论不会进入报告。真实供应商联调需要用户提供连接并主动触发，不作为自动测试动作。

### P6 完成任务内交互

- [ ] P6.1 在现有任务详情提供“协作分析”，自动使用当前任务；成员筛选只改变分析范围，不把子 Agent 变成另一个任务。第一次进入展示范围和能力，点击后分析，不先索要第二次运行。
- [ ] P6.2 将页面组织为“问题与证据、调整建议、优化验证”三个同任务区域，不做强制五步向导。规则分析是主动作，AI 复核是可选增强，模型配置和高级阈值收进紧凑设置。
- [ ] P6.3 问题列表优先显示具体成员、行为、影响和依据；展开后按事实、推测、反例、改法和验证项阅读。对已检查无发现、未检查、证据不足提供清楚说明，不把空列表画成全绿通过。
- [ ] P6.4 从问题定位原生事件、捕获或逻辑调用；交接问题能并排看发送与接收，重复读能比较参数和结果。保持任务、成员和原始事件深链接，返回报告时恢复选中项和滚动位置。
- [ ] P6.5 沿用用户确认的单行彩色轨迹和整页阅读方式：滚动后保留紧凑任务名称与轨迹，正文有足够高度；搜索、过滤和操作不占多排纵向空间。分析摘要可收起，不能把工具输出和模型内容挤进小滚动框。
- [ ] P6.6 完善大任务、无子 Agent、只有导入摘要、权限不足、删除、过期、取消和错误状态；覆盖中英文、键盘定位、屏幕较窄时的证据阅读。长列表有界渲染，禁止逐成员浏览器请求。
- [ ] P6.7 原实验入口保留为高级能力或案例入口，相关链接回到同一任务报告，不维护第二套互相矛盾的结论。支持从“优化验证”关联新任务并回到原问题。

阶段验收：用户从现有任务出发，无需阅读说明，就能完成“分析一次 → 看清一个问题 → 打开原文 → 知道下一步怎么改”。

### P7 关联优化后任务并验证收益

- [ ] P7.1 添加“关联优化后任务”，从现有任务列表选择已观测的新运行；外部记录走既有导入入口。保存基线、候选、关联原因和本次改动说明；两个采集任务或采集与导入均可比较，来源标签不变。
- [ ] P7.2 展示可比性检查：目标与输入、初始状态、模型、工具权限、环境、验收标准和非目标配置。未知与不一致单独列出；用户可以继续描述性对比，但确认不能抹掉已知差异。
- [ ] P7.3 建立逻辑角色或边界对应，支持合并、拆分、保留及人工修正。使用可验证的角色和行为线索，不按同名或临时 ID 硬配；未映射项显示未匹配。
- [ ] P7.4 用相同策略版本和阈值对两个快照分析，按问题及边界展示改善、仍存在、新增或无法判断。对方缺少数据不能算问题消失；策略版本不同需重算或标不可直接比较。
- [ ] P7.5 接入现有测试、明确验收记录或用户确认的验收项，分开显示任务状态与质量。无可靠验收显示“质量未验证”；AI 可解释或建议验收项，但不能靠自评分宣称完成质量无损。
- [ ] P7.6 并排比较真实墙钟耗时、模型调用、工具调用、输入输出及缓存 Token、可得费用。区分端到端和边界局部变化；不把并行耗时累加当节省，不把缺费用当零，不把分析费用并入执行费用。
- [ ] P7.7 保留每个 case、每次 rep 和各自链路；不把不同重复拼成一条完整链。单对任务标为单次观察，多次运行显示分布、缺失和逐任务回归；任何平均提升都不能遮住通过变失败。
- [ ] P7.8 提供“采纳、继续调整、保留原方案”的人工决定及理由，独立保存所依据报告版本。决定不覆盖测量结果；有回归或质量未验证时明确列出，不能给出系统已证明收益的结论。

阶段验收：无第二次任务时诊断可用；有第二次任务时能说明原问题是否改善、有没有新增问题、质量是否保住，以及速度或费用变化能支持多大范围的结论。

### P8 用官方客服案例完成演示和回归

- [ ] P8.1 固定并复用 kit 提交 `c43796287b83bec847db923f07131d1cc8de750d` 的数据、LICENSE 和来源清单；校验导入与现有数据一致。示例入口标“导入 · 官方公开历史案例”，合成流量另标合成，不能冒充本机采集。
- [ ] P8.2 演示“先看一个多 Agent 任务”：显示可识别成员、边界检查、证据缺口和候选，不要求先选 A/B。历史日志无完整接收上下文或逐事件时长时，不绘制假时间或伪造交接损失。
- [ ] P8.3 用 returns 的真实历史 A/B 演示“整体变好但个别任务回归”：应保留整体 22/24 到 23/24，同时突出 t01 某次优化后遗漏送达日期的失败。可从失败验收项跳到对应工具结果与回复。
- [ ] P8.4 用 diagnostics 的历史实验演示“任务通过但过程变贵”：检查 t10 原始与补跑记录，显示多出的订单路径及开销，允许展开核对必要性。不把其基线和 returns 的基线混成同一个版本。
- [ ] P8.5 用 orders 与 shipping 的相邻流量展示“待验证合并候选”，明确是合成流量提供的线索；没有该合并的真实对照就不显示已获收益。没有完整单循环实跑也不生成单循环获胜卡片。
- [ ] P8.6 补充最小自有测试数据覆盖重复读、合理复核、真实交接不足、同义转述、工具冲突、外部独立 Agent、缺正文、模型虚构引用和提示注入。测试数据标为测试样本，不与官方实验成绩混合。

阶段验收：官方案例可以完整走通新交互，也能展示其数据无法支持的判断。离线 smoke 只证明流程可运行，不标成模型质量评测。

## 五 第一版的最终验收场景

以下全部通过，才算完成本次产品闭环；付费模型的真实供应商联调单独记录，不以 mock 成功冒充已完成。

| 场景 | 必须看到的结果 |
|---|---|
| 无 API Key，打开已有多 Agent 任务 | 能运行规则检查，看到范围、事实和不足，监控保持关闭 |
| 主子 Agent 读取同一份文件 | 能定位两次读；缺接收上下文时不确证交接损失、不自动建议合并 |
| 子 Agent 是独立审查者 | 重复读作为事实保留，同时展示合理独立性的证据和反对合并理由 |
| 真实交接缺关键内容 | 指向发送、接收、下游行为；区分可证实缺口与语义解释 |
| 用户主动请求 AI 复核 | 清楚数据发往哪里；可取消；模型引用都能定位且费用单列 |
| 优化后更快但原来通过的任务失败 | 回归明确优先展示，不能用总分增长宣称无损收益 |
| 优化后 trace 缺失 | 对应问题为无法判断，不能显示已经解决 |
| 两次运行模型或验收标准不同 | 显示不可比因素，仍可阅读事实差异但不归因于合并 |
| 切换任务、刷新、原文删除或来源更新 | 不串任务、不显示旧结论为当前结论，不隐式重试付费请求 |
| 官方样例和自有记录并存 | 采集／导入清楚，历史模型记录／合成／测试身份不混淆 |

## 六 与文章及 kit 的对应

参考 [Anthropic 文章](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) 和 [固定版本的 single-agent-loop-kit](https://github.com/anthropics/single-agent-loop-kit/tree/c43796287b83bec847db923f07131d1cc8de750d)。其代码、流程和样例是输入；没有把某个 Claude Code skill 命令当作现成的在线 trace 诊断 API。

| kit 环节 | 第一版在本系统中的落点 |
|---|---|
| audit | 基于已观测任务审计实际成员与边界，给出事实、缺口和有条件候选 |
| baseline | 绑定当前任务与已有验收，记录比较口径；缺验收则质量未知 |
| merge | 给出应联合检查的成员和边界，用户手动改造后关联新任务验证 |
| fold | 建议将流程转为主循环的 skill 或直接工具，提醒保留硬约束并检验相邻任务 |
| as-tool / keep | 明确独立上下文、结构化交付物、外部所有权等保留条件 |
| compare | 对比每次真实运行的过程、质量与开销，突出回归和数据缺口 |
| upkeep | 保留报告版本和用户决定；自动维护提示词、消融执行和持续优化留后续 |

本系统的增量价值是直接复用用户已经抓到的证据，把每个建议连回原始轨迹，并跟踪优化后同一问题的变化。网页里的模型调用负责语义判断，不替代可验证事实、验收测试或用户决定。
