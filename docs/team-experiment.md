# 任务模式实验：什么时候保留单 loop，什么时候委派或组队

设计与实现说明，2026-10-29。契约：
[team-experiment.md](../openspec/contracts/team-experiment.md)。

## 1. 用户进来要回答什么

以一个任务为中心，依次回答：

1. 两种实现有没有完成同样的要求？具体哪一项退步或改善？
2. 完成同样要求时，哪一组更快、用量更少、波动更小？
3. 多出来的 Agent 做了什么？有多少实际并行、等待、交接和返工？
4. 我能否定位到造成差异的记录，回放当时的协作过程？
5. 下次遇到同类任务，应继续单 loop、委派独立工作，还是建立团队？

实验结论针对这个任务和配置；不能由一次样本推断所有任务、模型或产品。

## 2. 研究依据与用户声音

先完整阅读了 Diane Sarkis 于 2026-10-22 发布的
[When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)。
本文采用其中三项方法：按共享上下文判断拆分边界；共同的端到端验收；逐次改动并检查具体任务的通过/失败变化。
文章没有提供可直接用于本产品的通用推荐阈值。下文的界面、数据模型和判断规则是本项目设计。

[官方 Team 文档](https://code.claude.com/docs/en/agent-teams) 与
[Subagents 文档](https://code.claude.com/docs/en/sub-agents) 支持区分独立上下文、集中委派和团队协商。
它们持续更新；当前普通子 Agent 也可能通信，不能仅凭消息工具名判断 Team。

原始反馈是发现交互需求的线索，不能当作当前版本的普遍故障：

| 原始声音 | 由此设计的检查入口 | 证据局限 |
| --- | --- | --- |
| [8 个 reviewer 的个人实践，2026-04-17](https://www.endlessgalaxy.dev/blog/claude-code-agent-teams-lessons)：大量分派没有形成预期的互相讨论 | 声明模式与观测结构分开，能展开成员间消息及产物 | 单人案例；文中部分旧版能力描述已变化 |
| [Claude Code #24414，2026-02-09](https://github.com/anthropics/claude-code/issues/24414)：用户报告反复签到和空闲确认 | 按工作、消息、等待筛选，查看开始前的协调过程 | 历史报告，已因不活跃关闭 |
| [#29271，2026-02-27](https://github.com/anthropics/claude-code/issues/29271)：用户报告空闲与失效混淆、重复创建成员 | 保留显式状态和时间，未知状态不画作成功或空闲 | 特定旧版本报告，已标重复 |
| [#47930，2026-04-14](https://github.com/anthropics/claude-code/issues/47930)：用户报告通知确认循环 | 消息记录、重复交接和返工可定位 | 用户报告，未在本项目中独立复现 |

没有把上述案例的用量倍率或 Anthropic 研究系统的特定评测胜率写成推荐阈值。

## 3. 三种模式的区别

| 模式 | 组织方式 | 适合优先试验的任务 | 首要观察 |
| --- | --- | --- | --- |
| 单 loop | 一个上下文持续规划、调用工具、读取原始结果；工具调用本身也可并行 | 强依赖链、需要持续共享细节、低时延交互 | 验收退步、上下文压力、工具选择和重试 |
| 主子 Agent | 主 Agent 委派边界清楚的工作，接收结果并整合 | 独立检索、隔离大量临时输出、独立验证 | 实际工作重叠、交接损失、主 Agent 等待与整合 |
| Agent Team | 多个上下文围绕共享工作协商、互相检查与协调 | 需要讨论、交叉质疑和解决跨成员依赖的工作 | 同伴协作的具体证据及其质量收益、协调与返工 |

“多个 Agent”只证明参与数量；不能证明采用了 Team。界面同时显示用户声明的模式和记录支持的结构。
同伴消息也只证明发生通信，不自动证明通信有价值。缺少通信覆盖时，不能把未观察到消息解释为没有消息。

## 4. 现有可观测实现与本次增加的能力

既有原生团队管线有规范化 Agent、关系、任务、依赖、分派、活动和通信类型。
`team-topology.ts` 根据记录的关系推导结构；`team-metrics.ts` 计算团队内部工作、等待和协作指标；
任务阅读器提供成员切换、原始事件查看及历史轨迹。

这些原生证据有覆盖边界。例如父子关系不证明实际消息，日志间隙不证明等待，工具提议不证明执行。
现有 Codex / CodeArts 的基准原生 fixture 没有足够的发送方/接收方通信事实，因此仍标记通信不可用。
本次只在驱动提供明确通信记录时展示该实验的消息，不补全既有原生会话缺失的通信。
某些已有“加速估计”用任务时长总和与墙钟时间相除，只描述并行潜力，不能代替真实单 loop 对照。

新增的实验层固定任务和验收，在不同独立工作区分别执行配置，获得真正的对照 E2E。
实验报告保存来源标识、提示词指纹、验收和协作证据；不会修改原始会话或将抓包重复计费。

## 5. 信息架构与阅读路径

入口为现有工作台中的“任务模式实验”，地址 `#/team-experiment`。

```text
任务模式实验
  配置共同任务和验收 → 配置模式与各自提示词
  选择并行 / 顺序、重复次数 → 显式运行或导入报告
  质量与配置比较 → 建议与证据限制
  同步回放 → 成员轨迹 → 详细记录 → 原始会话定位
```

配置只占初始区域，结果阅读时可以收起。任务名称、紧凑回放控制和轨迹吸顶；
详细公开输出、工具记录和消息使用页面的阅读空间。每个成员一行，类型用颜色和文字同时区分。
详细记录有分页，防止大量事件把浏览器卡住。选择事件后查看其确切记录，避免只靠很细的方块定位。

## 6. 怎么做一次有解释力的实验

固定任务、代码提交、验收器和具名验收用例。分别填写模式、提示词、模型、工具、参数和环境。
每组至少重复 3 次是产品建议的最小观察门槛，不能视为统计显著性证明。

允许每组不同提示词；页面会说明这是“配置组合对比”。若要单独判断架构影响，
先保持提示词和其他变量相同，再只改变委派方式。之后再单独测试提示词优化。
模型未知、用量口径不明、样本不足或采集不完整，都需要保留其限制。

并行模式满足两边同时跑的工作流：每轮先准备所有独立工作区，再启动各驱动。
共享机器、网络和模型服务仍可能互相争用；并行更快结束实验，不保证测量不受干扰。
需要判断性能时，应再做顺序重复实验，比较结论是否改变。

## 7. 指标与解释边界

| 维度 | 展示 | 解释 |
| --- | --- | --- |
| 准 | 独立通过数、逐用例双方通过 / 仅一侧通过 / 双方失败 / 未知 | 主 Agent 宣称完成不能代替验收 |
| 快 | 实测 Agent E2E、配对耗时比、模型/工具调用、实测 TTFT/TPOT | 准备与验收另列；累计调用时长允许重叠 |
| 稳 | 重复次数、缺失次数、中位数、P95、标准差、CV | 小样本只作描述，不给显著性结论 |
| 用量 | 输入、输出、思考、缓存读写、校正总 Token | 明确包含关系，缺失不填零；Token 不等于费用 |
| 协作 | 不同成员工作重叠、活跃峰值、显式等待、消息/交接/返工 | 等待和返工需要事件证据，不由空白或同文件访问猜测 |
| 上下文 | 明确记录的上下文 Token | 是诊断信号，不能据此断言上下文导致质量退步 |

工作重叠按不同成员的活动区间计算，同一成员同时出现模型与工具不会算作两名成员。
驱动应把实际工作与等待分开，不能把包含等待的整段任务生命周期当作工作区间；
这里的重叠不是 CPU 占用或已认证的实时模型并发。
累计等待先对每个成员的等待区间求并集再求和，因此可能大于任务墙钟；不会标为“任务被阻塞时长”。
通信 Token 是已有总量中的诊断切片，不再加一次。公开模型输出可读，系统不会生成或补全未记录的思考。

## 8. 如何给建议

规则公开、证据可点，不以综合分数掩盖取舍：

1. 先检查独立验收、具体用例翻转、样本与覆盖；有未知时先补证据。
2. 有质量退步的配置不能只因更快而被推荐。
3. 同等验收下比较实际耗时与校正 Token；一快一省属于取舍，保留双方数据。
4. 再用协作记录解释可检验的假设，例如独立工作是否实质重叠、交接是否很多、是否显式返工。
5. 推荐限定为当前任务/配置的选择假设，附控制变量复测方向。

合成数据永远显示演示性建议。三种模式不预设优劣；四个合成场景分别演示单 loop 更合适、
主子 Agent 有收益、Team 改善验收、证据不足。导入报告也不能因为字段写着 Team 就获得 Team 优势。

## 9. 回放是什么

回放使用一个任务相对时间游标，双方从各自 Agent 执行起点对齐。支持播放、暂停、拖动、
前后关键事件、速度、轮次、成员及事件类型筛选。游标只控制已记录的历史，不重新发请求或执行工具。
没有事件的时间显示没有已知记录；不自动补成 idle/waiting。

消息、交接与依赖可展开查看记录的发送方、接收方和前置事件；它们的因果意义仅限来源明确声明的关系。
有真实 sessionKey/eventId 才提供原始会话跳转。模拟记录不生成假的原始会话链接。

## 10. 模拟、内置流程验证与真实运行

- **离线模拟**：四组确定数据，展示不同结果、协作记录和回放，不执行任何模型或工具。
- **内置流程验证**：显式按钮执行固定本地任务、隔离工作区、多个子进程和独立验收，验证运行框架。
  仍是 synthetic；模式标签不会把固定脚本变成真实 Agent。自定义任务配置不会被这个按钮偷偷执行。
- **真实实验**：编辑导出的计划，配置实际驱动与独立验收命令，通过 CLI 显式执行。
  模型费用及权限由所接驱动决定。系统未宣称任意 GUI 仅填写名称即可被自动操控。

```sh
npm run build
# 校验计划并查看配置，不启动驱动
npm run team:experiment -- config/team-experiment.example.json
# 编辑绝对路径和驱动后，明确执行；输出目录必须不存在
npm run team:experiment -- ./my-team-experiment.json --execute --output ./experiment-results/task-001
```

驱动读取 `BENCHMARK_CONTEXT` 中的共同任务、当前 variant、精确提示词、提交和工作区；
在 `BENCHMARK_WORKSPACE` 完成工作，写 `BENCHMARK_RESULT_PATH` 为既有 benchmark telemetry。
协作记录写 `TEAM_EXPERIMENT_EVIDENCE_PATH`，形状以 canonical types 和导出样本为准。
驱动必须等待实际完成，不能只提交 GUI 任务就退出。
`actualModel` 必须覆盖本轮完整模型配置（包括成员），不是只读主 Agent 的标签。
成员模型未知、切换或不符合计划时，应保留未知/不一致；页面的一致性是对驱动声明的
检查，不是向厂商独立认证模型身份。混合模型需在配置与参数中明确列出各角色及固定模型。

独立验收器随后检查最终产物，写 `BENCHMARK_VERDICT_PATH` 及 `TEAM_EXPERIMENT_CASES_PATH`。
具名用例应与计划完全一致；汇总和具名结果矛盾时不能认证质量。
可信验收器应在 Agent 工作区外；本地进程运行框架不是隔离恶意代码的安全沙箱。

执行超时或取消会终止所拥有的进程组，保留已完成记录；外部 GUI 仍需其驱动管理。
真实厂商模型/GUI与跨平台清理必须分别验收，内置样例通过不代表这些能力已验收。
CLI 运行合成驱动时应显式添加 `--synthetic`，以保留合成来源标识。
页面内置演示接口输入最多 512 KiB，只接受名称、次数、调度、模式与提示词，
不会接收或执行任意仓库路径、驱动命令或验收命令。

## 11. 数据与默认开关

实验 JSON 和工作区与真实采集库分离；导入、回放、语言切换不启动监控或抓包。
监控、代理和 Frida 保持默认关闭。实际采集仍由原来的明确开关控制。
本功能不改证书、系统代理或真实会话。报告导入有大小、数量、文本和引用约束，内容作为纯文本显示。

## 12. 验收记录（2026-10-29）

最终在独立工作目录验证59个本次文件，保留其他本地草稿。Node24.19.0，
类型、lint、三阶段构建、安装包产物检查和CLI计划校验通过。
完整回归：330文件、3966项通过、0失败、1项既有SQLCipher环境条件跳过，255.55秒。

浏览器实测：

- 直接打开并刷新 `#/team-experiment` 正确；旧团队路由前缀冲突已修复并补2项回归。
- 点击内置配对实验，2组×3次、6/6独立验收通过；三轮的两个驱动区间确有重叠。
  这验证本地进程运行框架，不代表真实模型并行收益。
- 四种离线情景、建议定位、Team消息公开正文、播放/暂停/下一事件均可操作。
- 691×611的实际窗口中，正文完整显示在吸顶轨迹下方；修复了定位到详情底部导致正文被遮挡的问题。
- 运行错误、覆盖和未知验收可按轮次展开；大报告用例按100条分页，关闭不挂载。
- 导出Blob与真实FileReader重导完整字段由组件测试验证；未据此宣称原生文件对话框已验收。
- 页面控制台无错误/警告；运行后监控enabled=false、代理和Frida running/starting=false。

9项性能诊断通过。HTTP、HTTPS CONNECT、近2MiB场景各100个预热后配对样本、
并发4、104条捕获与208份原文校验全部保留；额外E2E P95分别8.345/10.474/9.903ms。

完整回归中曾有一项极限采集p99=52.560ms超过50ms，失败记录保留。阶段诊断发现重复
序列化多MiB身份字段，以及先前计时未包含的SQLite COMMIT。正式修复复用每条完整身份
SHA形成带域和版本的快照摘要，保持身份ID、原文、关联、原子性和耐久性；旧摘要正常入库时
刷新一次，后续乱序/重复零写入。新增11项语义测试，不放宽负载、断言、采样或预算。
最终完整回归的两种极限负载p99/max为41.320/37.782ms，均低于50ms。

这些是当前环境下的受控功能与性能证据，不是厂商模型、Windows、长时间运行或所有NFR
的通用认证。最差会话slim查询15.132ms在现有60ms预算内，历史15ms告警未因此宣称消除。
真实驱动、成员模型确认及实际任务结论仍需用自己的任务和验收重复验证。
