# RSI 功能覆盖清单

对照 [design.md](design.md) 逐项记录现状，数据来自 2026-11-07 的真实运行。优化者和被优化 Agent 用 DeepSeek（`deepseek-flash`），监控用 `gpt-6.1-sol`，运行环境是 M1 8GB 上的 Colima（4 核 4GB）。

补充验证在 2026-11-08 完成，见“干净克隆走查”和 [scripts/rsi-e2e/human-flows.mjs](../../scripts/rsi-e2e/human-flows.mjs)。

状态的含义：

- **真实**：用真实模型和真实容器跑通过，有账本记录。
- **脚本模型**：真实容器、真实服务和真实闸门，但模型回复是脚本化的。
- **仅测试**：只有自动化测试覆盖。
- **未做**：没有实现。

## “跑起来”的 5 条验收标准

| # | 标准 | 结果 | 证据 |
| --- | --- | --- | --- |
| 1 | 无人值守连续跑完至少 3 轮，失败时停在明确状态 | 通过 | `demo-full` 无人值守跑了 4 轮（晋级、拒绝、拒绝、拒绝）。OpenCode 小题集连续 3 轮没提交后，自动转为“需要帮助” |
| 2 | 每轮能查到 PRD、提交、评测结果、轨迹、token、耗时、监控结论 | 通过 | 在迭代详情页逐项看过真实数据 |
| 3 | 注入已知作弊补丁，按题目特判和改测试两类全部拦下 | 通过，有限制 | 10 个作弊提交全部拦下：L1 拦 6 个，真实监控拦 4 个。2 个正常对照无误报。这些是模板补丁，见“已知限制” |
| 4 | 人工能回退到任意历史版本，并把禁令带入下一轮 | 通过 | 真实回退打断了运行中的会话，新会话从指定版本开始。禁令和思路进入下一轮 brief，优化者采纳了思路 |
| 5 | 重复评测给出分数波动范围，晋级判定考虑波动 | 通过，波动数据少 | `opencode-full` 基线两次重复得 14 和 15。demo 的基线每次都是 0，δ 为 0 |

## 真实运行结果

| 任务 | 被优化对象 | 基线（训练 / 封存） | 过程 |
| --- | --- | --- | --- |
| `demo-run` | 削弱版 mini-agent，小题集 | 0/6，0/3 | 第 1 轮拒绝；第 2 轮 6/6、封存 3/3，因 token 增幅挂起；人工批准后晋级并达到目标；最终留出集 3/3；采纳并导出补丁 |
| `demo-full` | 削弱版 mini-agent，完整题集 | 0/15，0/9 | 第 1 轮自动晋级（14/15、封存 8/9）；第 2 轮 13 分，未超过噪声带被拒；第 3 轮 15/15，但封存 7.33 低于父代 8，被封存集拒绝；第 4 轮 14 分被拒 |
| OpenCode 小题集 | OpenCode 2.1.3 | 6/6，3/3 | 基线已满分，3 轮优化者会话都没提交，转为“需要帮助” |
| `opencode-full` | OpenCode 2.1.3，完整题集 | 14.5/15，8/9，δ=2.83 | 前 4 轮优化者没有提交（1 轮挂起超时，3 轮用完 200 万 Token）。人给思路并调高上限后，第 5 轮提交了一个修复；候选 15/15，增益 0.5 未超过噪声带，被正确拒绝 |

总花费 5.88 元（余额 53.12 → 47.24），预算上限是 22 元（约 6 新西兰元）。监控走 Codex 登录态，不计入这笔。

OpenCode 那个候选值得单独看：优化者从基线的失败题 `rsi-escaped-columns` 查到，非交互模式下取消“网页搜索服务商”表单时，进程会以退出码 1 结束，即使模型已经完成了任务。补丁在 [examples/opencode-websearch-form.patch](examples/opencode-websearch-form.patch)。这是优化者的判断，平台只验证了分数，我们没有独立确认它是上游的真实 bug，也没有合入任何地方。

## 真实运行查出并修复的问题

这些问题在脚本模型和单元测试下都没有暴露，修复都带了测试：

| 问题 | 后果 |
| --- | --- |
| Agent 非零退出一律算基础设施错误 | 一个会崩溃的候选就能让整个任务暂停 |
| 优化者镜像的 npm 版本不存在 | 优化者根本起不来 |
| 优化者收到全历史 bundle（OpenCode 591MB，上限 256MiB） | 大仓库无法优化 |
| Agent 收到最终回复就退出，代理随之中止上游，丢失最后的用量 | 成功且已计费的运行被判基础设施错误，一度 21 次里 11 次，任务暂停 |
| 用量轮询一次抖动就作废整次运行 | 浪费已花的 Token |
| 终止优化者时的竞态 | 机器繁忙时丢弃有效提交 |
| 数据目录晚于服务出现时，文件监听没挂上 | 新用户的页面一直是旧数据 |
| 并发打开共享索引报 `database is locked` | 约十分之一的命令行调用失败 |
| 每次账本变化都重放整个账本 | 单次页面请求约 800ms，且随任务增长 |
| 从页面新建的任务没有监控 | 每轮都会被挂起 |
| 第一轮看不到基线的逐题结果 | 优化者只能盲猜 |
| 连续 3 轮没提交后，人点“继续”不生效，执行器满 CPU 空转 | “给思路再继续”这条路是坏的 |
| 迭代上限刚到就暂停，最后一轮已提交却不评测 | 上限 N 实际只评测 N-1 轮 |
| 基线已达目标或超不过噪声带时仍继续跑 | 白白消耗 Token |
| 共用监控桥时，繁忙的 429 被当成监控缺失 | 无故挂起，要人工重跑 |
| 人工批准的理由没进决定记录 | 看不到是谁、为什么放行 |

## 干净克隆走查

从 `git clone` 开始，在一台新建的虚拟机上按使用指南走一遍：`npm install`、`npm run build`、`rsi doctor`，然后从零构建全部镜像并跑隔离闭环（`p4-loop`）。全部通过，约 9 分钟，模型回复是脚本化的。

走查发现 3 处使用问题，都已修复：

| 问题 | 处理 |
| --- | --- |
| `npm install` 会改动 lockfile，克隆后工作区不干净 | 更新 lockfile |
| 指南要求 `doctor` 全部通过，但 `upstream` 这时必然是 false，要到后面才设置模型 | 指南写明这一点 |
| `colima start` 会把 Docker 的当前 context 切到这台虚拟机 | 指南写明怎么切回去 |

`brew install` 这一步没有走，这台机器已经装好。

## 题库

| 题库 | 题数 | 校验 | 难度实测 |
| --- | --- | --- | --- |
| 标准题库 | 30 | 全部通过，容器内实跑，变异杀伤率不低于 0.7 | OpenCode + DeepSeek 完整题集 14.5/15，太容易 |
| 进阶题库 | 12 | 全部通过，容器内实跑，变异杀伤率 0.75～1.00。放到平台上用脚本模型跑过：基线 0 分且没有基础设施错误，应用参考修复的候选训练集 6/6 | 强模型盲测 8 题全对；DeepSeek 没有测 |

盲测的做法：只给题面和代码，隐藏测试判分，每题独立一次，用 `gpt-6.1-sol` 低思考强度。

| 版本 | 内容 | 结果 |
| --- | --- | --- |
| 第一版，18 题 | 约 450 行的小项目，两到三个根因 | 抽 6 题，全对，每题约 1 分钟。结构也千篇一律，缺陷总在同样的两个文件。放弃 |
| 第二版，12 题 | 长规格实现、多文件排查、复杂度要求、确定性并发 | JavaScript 和 Python 的 8 题全对，每题约 1 分钟。Go 的 4 题没有盲测 |

结论是模型写的这种规模的题难不倒同级别的强模型，继续迭代意义不大，所以停在第二版。它比标准题库复杂得多，可能对较弱的模型有区分度，但这一点还没有数据。要优化最强的 Agent，需要来自真实项目的题，比如设计中标为“之后”的 Verified Mini。

## 明确不在这一版

设计中标为“之后”或“先不做”：

- 云端托管、多租户、额度控制。每个人在自己机器上运行。
- Verified Mini、Multi-SWE-bench 和近千题规模。
- `docker context` 经 ssh 放到另一台机器评测。
- Windows 和 GUI 形态的评测。
- OTLP 采集渠道，设计中是备用项。现在用模型代理和会话库。
- 把 OpenCode 接入 task-health 的富化（`server/task-health/collector.ts` 只支持 codex、claude、codeagent）。

## 已知限制

- **作弊样本是模板**。注入和校准语料证明这几类做法能被拦住，不能证明真实作弊都能被发现。完整校准的高分不能外推到真实攻击，公开研究里监控在 SWE 类任务上只抓到 42%～65%。
- **题库都是模型写的**。标准题库对 OpenCode 加 DeepSeek 太容易；进阶题库对强模型同样太容易，对 DeepSeek 还没有测。真正优化成熟的 Agent 需要来自真实项目的题。
- **分数上涨只在演示 Agent 上验证过**。它是故意削弱的，修的是明显缺陷。OpenCode 这次的候选虽然分数更高，但没有超过噪声带，不能算确认的提升。
- **噪声带是用 2 次重复标定的**。为了省钱，真实运行用了 2 次，设计建议 3 次；δ 因此偏大也偏不稳。要给 OpenCode 这样的 Agent 留出空间，需要更多重复和更难的题。
- **优化者有一轮挂起了 28 分钟**，模型请求已结束，之后再无动静，直到时限结束。容器已销毁，没有定位到原因。现在这样的轮次会提前结束并留下进程和输出，但新机制只用脚本模型验证过，真实模型下还没有再现这个挂起。
- **优化者每轮 Token 上限把缓存也算进去**，默认 200 万对大仓库偏小，见使用指南。现在任务运行中也能调整。
- **候选补丁和隐藏测试在同一个评估容器里运行**，补丁理论上可以影响测试过程。
- **L1 拒绝的类别会告诉优化者**，理论上可以被用来低速试探规则。
- **账本中段被改动，要到 `ledger verify` 或下次重建才发现**。这是为了不在每次读取时重放整个账本。
- **只在 macOS + Colima 上验证过隔离**。
