# RSI P0 实测报告

实测日期 2026-11-07，机器 M1 8GB，Colima 0.10.3（profile `rsi`，vz，4 核 4GB，`--mount none`），Docker 29.9.3，OpenCode 2.1.3（commit 4d30794bcf）。

**这份结论的边界：** 样题只有一道，而且是单文件的简单 bug。隔离、流程和构建的结论可信。真实模型只跑过这一道题、一次，耗时和内存**不能外推到难题或 30 题**。按用户要求，没有跑完整评测和真实模型下的并发 2。

## 真实模型结果（DeepSeek V4.1 Flash）

2026-11-07 用 `deepseek-flash`（OpenCode 目录里的名称是 DeepSeek V4.1 Flash）跑一次，并发 1。

| 项目 | 结果 |
| --- | --- |
| 判分 | 通过，封存测试 5/5 |
| 代理和会话库 token | 29671 对 29671，差值为 0 |
| 请求数 | 6 次，其中 1 次是生成标题的辅助请求 |
| 缓存命中率 | 前两次为 0，之后 96%～97% |
| 耗时 | 整个 run 15.5 秒，其中模型调用约 6 秒 |
| 内存峰值 | 容器 386MB，VM 834MB（当时还有一个题库校验容器在跑，所以 VM 数字偏高） |
| 隔离 | 全部通过 |
| 密钥 | 搜索全部输出文件，没有出现 |

Token 总量把缓存命中的输入也算在内。这道题 6 次请求共约 2.97 万 token，其中约 2.24 万命中缓存。

接入时发现的两件事，P2 必须照做：

- 用 OpenCode 内置的 `deepseek` provider（模型 `deepseek/deepseek-flash`），只覆盖 `baseURL` 和 `apiKey`。这个模型要求把 `reasoning_content` 回传，用通用兼容 provider 可能在第二步出错；这一点来自模型目录的声明，没有实测反例。
- 模型默认开思考，探测请求里 16 个输出 token 全部花在 reasoning 上。`max_tokens` 不能太小，这次用 8192，单 run 预算 30 万。

## 五个问题的答案

| 问题 | 答案 | 证据 |
| --- | --- | --- |
| 8GB 上并发 2 稳定吗 | 假模型下稳定，真实模型只测过并发 1 | 并发 2 连跑 3 轮，6 个 run 全部通过，无 OOM；VM 峰值 673～986MB；宿主可用内存 34%～36% |
| 优化者在 Linux 容器里怎么登录 | CLI 能跑，登录未验证 | Codex 0.167.0 在 linux/arm64、无网络容器里能启动；支持 `--with-api-key`、`--device-auth`。没有实际登录过 |
| 容器能访问宿主回环吗 | 不能 | 见下方隔离矩阵。4173 端口当时没有服务在监听，这一项只能说明连接失败 |
| OpenCode 的请求都走代理吗，token 对得上吗 | 都走代理，差值为 0 | 被优化容器只接 internal 网络。假模型 3 次请求 360 token，DeepSeek 6 次请求 29671 token，都和会话库完全一致 |
| 构建多久，依赖怎么限制联网 | 首次 3 分 19 秒，缓存约 2 秒；只有构建时联网 | 镜像 209MB。构建时拉依赖，运行时在 `--internal` 网络下启动正常，不需要联网 |

## 隔离矩阵

每个 run 都在被优化容器内部实测，宿主机上有一个已确认存活的回环服务（18765 端口）作为靶子。

| 检查项 | 预期 | 实际 |
| --- | --- | --- |
| 公网 IP、公网域名 | 不通 | 不通 |
| `host.docker.internal`、`host.lima.internal`、`192.168.5.2` 上的宿主端口 | 不通 | 不通 |
| internal 网络网关 `172.18.0.1` 上的同一端口 | 不通 | 不通（这个地址是虚拟机，不是宿主机） |
| 上述地址的 4173 端口 | 不通 | 不通（当时没有服务监听） |
| `/var/run/docker.sock` | 不存在 | 不存在 |
| 宿主文件 | 看不到 | 看不到 |
| 模型代理 | 能通 | 能通 |

虚拟机本身也没有挂载任何宿主目录：`mount` 输出里没有 virtiofs，也没有 `/Users`。

## 实测中修掉的问题

这些都是探针脚本的问题，修复时没有放宽任何隔离：

1. `path.join` 会吃掉 `repo/.` 结尾的 `/.`，文件被拷到子目录。
2. `docker create -w` 会把工作目录预先建成 root 所有，普通用户写不进去。
3. `docker cp` 保留宿主的属主和权限，`--cap-drop ALL` 的容器里 root 也改不了。
4. `docker exec` 不带 `-i` 时 stdin 不进容器，OpenCode 读到了空配置，报 `Model unavailable`。
5. 宿主文件权限是 0600 时，容器用户读不了。当时这个基础设施错误被判成了 `fail`。

## 带给 P2 的要求

**必须做：**

- 导出 diff 前先 `git add -A`，再 `git diff --cached --binary`。现在的 `git diff HEAD` 漏掉新建文件，只是样题碰巧没有新建文件。
- 数据进容器统一走 tar 流或 stdin，不依赖 `docker cp` 的属主行为。工作目录由容器用户自己创建。
- 严格区分基础设施错误和判题失败。评估器自身的权限、IO、启动错误一律是 `infra_error`，绝不能算成 `fail`。
- 没有任何请求时代理日志文件不存在，这不能掩盖真正的错误。
- 内存用 cgroup 的 `memory.peak` 读取，在销毁容器前采集，不靠 `docker stats` 采样。
- `maxTokens` 不能写死 1024，要能配置。预算预留现在按请求字节数算，真实请求带着工具定义，容易误触发 429，要按真实请求校准。
- OpenCode 配置用新格式（`providers.<id>.package`、`settings`），运行命令是 `opencode run --standalone --auto --format json --model <provider>/<model>`。

**已知局限，需要写进契约：**

- 候选补丁和隐藏测试在同一个容器、同一个进程树里运行，所以补丁理论上能干扰测试框架（`process.exit`、改 `assert`）。用例数量核对挡住一部分，但挡不住全部。P5 要对被优化 Agent 产出的补丁也做这类扫描。
- OpenCode 每次会多发一次生成标题的辅助请求（3 次里的 1 次）。这部分 token 算进总量，比较时不扣除。

## 还没验证的事

- 优化者容器的实际登录和厂商域名白名单。
- OTLP 这一路数据，它不阻塞第一版。
- 平台按候选 commit 重新构建的完整流程。P0 只验证了构建基线 OpenCode。
